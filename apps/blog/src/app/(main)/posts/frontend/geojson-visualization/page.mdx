## GeoJSON 포맷

GeoJSON은 지리 데이터를 표현하기 위한 JSON 포맷입니다. 이름 그대로 그냥 JSON이라, 별도의 파서 없이 `JSON.parse`만으로 읽힙니다.
가장 바깥은 보통 `FeatureCollection`이고, 그 안에 여러 개의 `Feature`가 들어 있습니다. 시도 지도라면 서울, 부산, 경기도 같은 각 지역이 하나의 Feature가 됩니다.

Feature 하나의 구조를 들여다보면 이렇게 생겼습니다.

```json
{
  "type": "Feature",
  "properties": { "name": "서울특별시", "name_eng": "Seoul", "code": "11" },
  "geometry": {
    "type": "Polygon",
    "coordinates": [
      [
        [127.022, 37.699],
        [127.025, 37.699],
        [127.026, 37.700]
      ]
    ]
  }
}
```

- `properties`에는 지역명, 코드 같은 부가 정보가 들어갑니다. 화면에 라벨을 띄우거나 hover 이벤트에서 활용할 값들입니다.
- `geometry`가 실제 도형 데이터입니다. `type`과 `coordinates`로 이루어집니다.
- 좌표는 `[경도(longitude), 위도(latitude)]` 순서입니다. 위도-경도 순서로 알고 있으면 여기서 자주 실수합니다.

### Polygon과 MultiPolygon

지도를 그리려면 두 가지 geometry 타입만 알면 됩니다.

`Polygon`은 좌표 링(ring)의 배열입니다. 첫 번째 링은 바깥 경계선이고, 그 뒤에 오는 링들은 도형 안의 구멍(예: 호수처럼 비어 있는 영역, 혹은 광역시가 도(道) 안에 박혀 있어 도 폴리곤에서 그 부분을 빼낸 도넛 형태)을 뜻합니다. 그래서 좌표가 `[[[...]]]`처럼 세 겹으로 중첩됩니다.

`MultiPolygon`은 Polygon들의 배열입니다. 섬이 여러 개라 한 덩어리로 표현할 수 없는 지역이 여기 해당합니다. 제주도나 경상남도처럼 부속 섬이 많은 곳이 MultiPolygon이 됩니다. 중첩이 한 단계 더 깊어 `[[[[...]]]]`가 됩니다.

이 글에서 쓰는 시도 경계 데이터는 17개 시도 중 7개가 Polygon, 10개가 MultiPolygon입니다. 두 타입을 모두 다뤄야 한다는 뜻입니다.
두 타입이 좌표 깊이가 다르다는 점만 통일해주면, 나머지 처리는 똑같이 할 수 있습니다.

```js
// Polygon과 MultiPolygon을 "폴리곤들의 배열"이라는 같은 형태로 통일한다.
function extractPolygons(geometry) {
  if (geometry.type === 'Polygon') {
    // Polygon 하나를 길이 1짜리 배열로 감싸 형태를 맞춘다.
    return [geometry.coordinates];
  }
  if (geometry.type === 'MultiPolygon') {
    // MultiPolygon은 이미 폴리곤들의 배열이라 그대로 반환한다.
    return geometry.coordinates;
  }
  // 점/선 등 이 데모에서 다루지 않는 타입은 무시한다.
  return [];
}
```

이렇게 한 번 감싸두면, 이후 코드는 geometry 타입을 신경 쓰지 않고 "폴리곤 → 링 → 좌표"라는 일관된 중첩 루프로 처리할 수 있습니다. 여러 지역(Feature)을 한꺼번에 다룰 땐 여기에 Feature 순회가 하나 더 붙어 "feature(지역) → polygon(덩어리) → ring(경계선) → [경도, 위도] 점" 네 단계가 됩니다.

## 1단계: 좌표 범위 구하기 (bounding box)

데이터에 들어 있는 좌표는 경도 124~132, 위도 33~38 사이의 실수들입니다. 이걸 그대로 화면에 찍으면 좌상단 구석에 점 하나로 뭉쳐버립니다.
화면에 맞추려면 먼저 "이 데이터가 차지하는 지리적 범위"가 얼마인지 알아야 합니다. 경도와 위도 각각의 최소·최대값, 즉 **bounding box**를 구하는 일입니다.

특별한 기교는 없습니다. 모든 좌표를 한 번 훑으면서 최솟값과 최댓값을 갱신하면 됩니다.

```js
// FeatureCollection 전체를 순회해 경도/위도의 최소·최대값을 구한다.
function computeBounds(features) {
  let minLng = Infinity;
  let minLat = Infinity;
  let maxLng = -Infinity;
  let maxLat = -Infinity;

  for (const feature of features) {
    for (const polygon of extractPolygons(feature.geometry)) {
      for (const ring of polygon) {
        for (const [lng, lat] of ring) {
          // 좌표가 [경도, 위도] 순서임을 기억하자.
          if (lng < minLng) minLng = lng;
          if (lng > maxLng) maxLng = lng;
          if (lat < minLat) minLat = lat;
          if (lat > maxLat) maxLat = lat;
        }
      }
    }
  }
  return { minLng, minLat, maxLng, maxLat };
}
```

이 함수를 데이터에 돌리면 경도는 `124.61 ~ 131.87`, 위도는 `33.11 ~ 38.61`이 나옵니다.
제주도 남쪽 끝에서 강원도 북쪽 끝, 그리고 동쪽 끝 울릉도까지를 모두 감싸는 사각형입니다. 이 사각형을 화면 크기에 맞게 펼쳐 넣는 것이 다음 단계입니다.

## 2단계: 경위도를 화면 좌표로 투영하기

지구는 둥근 공이고 화면은 평평합니다. 둥근 표면의 좌표를 평면에 펼치는 작업을 **투영(projection)**이라고 부릅니다. 투영 방식에 따라 지도의 모양이 달라집니다.

가장 단순한 투영은 경도를 x로, 위도를 y로 그대로 쓰는 방식(equirectangular)입니다. 적도 근처에서는 크게 문제없지만, 우리나라처럼 위도가 높은 지역은 가로로 길쭉하게 늘어나 보입니다.
그래서 웹 지도 타일이 쓰는 **구면 메르카토르**(spherical Mercator)와 같은 공식을 적용합니다. 위도가 높아질수록 세로 간격을 점점 벌려주는 방식입니다. 다만 실제 Web Mercator 좌표계(EPSG:3857)가 갖는 지구 반지름·타일 스케일 상수는 생략하고 공식의 모양만 가져온 형태라, 타일 지도와 좌표가 호환되지는 않습니다. 공식은 다음과 같습니다.

```js
// 경도는 라디안으로 변환해 x 값으로 쓴다.
const lngToX = (lng) => (lng * Math.PI) / 180;

// 위도를 Web Mercator의 y 값으로 변환한다(고위도일수록 간격이 벌어진다).
const latToY = (lat) => {
  const rad = (lat * Math.PI) / 180;
  return Math.log(Math.tan(Math.PI / 4 + rad / 2));
};
```

이 두 함수는 뒤에 나오는 `createProjector`에서도 호출하므로, 같은 모듈 상단에 두거나 `createProjector` 안에 함께 넣어야 합니다. 그래야 투영 코드만 떼어 써도 `lngToX is not defined` 같은 오류가 나지 않습니다.

`latToY`의 `Math.log(Math.tan(Math.PI / 4 + rad / 2))`는 Web Mercator의 표준 정의 그대로입니다(`Math.PI / 4`는 45도의 라디안 값). 유도 과정은 이 글의 범위를 넘으므로 결과 식만 그대로 씁니다. 위도가 커질수록 `log`·`tan` 조합이 y를 점점 빠르게 키웁니다.

x는 경도를 그대로(degree) 쓰고 y만 Mercator 공식으로 계산하면, 지도가 가로로 길게 늘어진 한 줄로 찌부러집니다. 원인은 두 축의 스케일이 어긋나는 것입니다. 가로축은 큰 숫자 그대로인데 세로축만 아주 작은 값으로 계산되어, 세로 방향이 거의 0으로 눌립니다.

숫자로 보면 이렇습니다. x는 degree 그대로라 범위가 약 7.3(경도 폭 131.87−124.61≈7.3도)인데, y는 `latToY`를 거치며 약 0.12라는 무차원 값(이 위도 범위를 `latToY`에 통과시킨 폭)이 됩니다. 같은 `scale`을 곱하면 세로가 가로보다 60배쯤 작게 그려집니다.
y가 작은 것은 `log` 변환 때문이 아닙니다. `latToY`의 출력이 라디안과 같은 차수의 작은 무차원 값이기 때문입니다(degree→radian 변환만으로 약 1/57배). Mercator `log` 변환 자체는 이 위도 범위에서 y 크기를 거의 바꾸지 않습니다(오히려 약간 키웁니다). x와 y는 **같은 공간**(메르카토르)에서 계산해 스케일을 맞춰야 합니다. 그래서 경도도 같은 공간으로 옮기는 `lngToX`를 따로 둡니다.

투영 함수와 bounding box가 준비되면, 이제 화면 크기에 맞게 스케일과 위치를 계산합니다.

```js
function createProjector(bounds, width, height, padding) {
  const { minLng, minLat, maxLng, maxLat } = bounds;

  // bounding box의 모서리를 Mercator 공간으로 옮긴다.
  const xMin = lngToX(minLng);
  const yMin = latToY(minLat);
  const yMax = latToY(maxLat);

  const geoWidth = lngToX(maxLng) - lngToX(minLng);
  const geoHeight = yMax - yMin; // max - min 순서라 항상 양수

  // 가로/세로 중 더 빡빡한 쪽에 맞춰 스케일을 정해 비율이 찌그러지지 않게 한다.
  const usableW = width - padding * 2;
  const usableH = height - padding * 2;
  const scale = Math.min(usableW / geoWidth, usableH / geoHeight);

  // 남는 여백을 반씩 나눠 지도를 가운데로 모은다.
  const offsetX = padding + (usableW - geoWidth * scale) / 2;
  const offsetY = padding + (usableH - geoHeight * scale) / 2;

  return ([lng, lat]) => {
    const x = (lngToX(lng) - xMin) * scale + offsetX;
    // Mercator y는 위로 갈수록 커지지만 화면 y는 아래로 커진다. 그래서 yMax 기준으로 뒤집는다.
    const y = (yMax - latToY(lat)) * scale + offsetY;
    return [x, y];
  };
}
```

이 코드에서 확인할 점은 두 가지입니다.

- `scale`을 가로·세로 비율 중 **더 작은 값**으로 잡았습니다. 한쪽에만 맞추면 다른 축이 넘쳐 잘리거나 비율이 망가집니다. 작은 쪽에 맞춰야 도형 전체가 안에 들어오면서 가로세로 비율도 보존됩니다.
- 화면 좌표계는 위쪽이 0이고 아래로 갈수록 y가 커집니다. 반대로 위도는 위로 갈수록 큽니다. 그래서 `yMax - latToY(lat)`로 위아래를 뒤집어줘야 북쪽이 화면 위로 갑니다. 이 부호 하나 빠뜨리면 지도가 거꾸로 뒤집힙니다.

## 3단계: 폴리곤을 SVG path로 변환하기

투영 함수까지 준비되면 나머지는 단순합니다. 각 지역의 좌표 링을 SVG `path`의 `d` 속성 문자열로 바꾸기만 하면 됩니다.

`path`의 문법은 간단합니다. 첫 점은 `M`(move to)으로 펜을 옮기고, 이후 점들은 `L`(line to)로 선을 잇고, 마지막에 `Z`로 도형을 닫습니다.

```js
// 좌표 링 하나를 SVG path의 d 속성 문자열로 만든다.
function ringToPath(ring, project) {
  return ring
    .map(([lng, lat], i) => {
      const [x, y] = project([lng, lat]);
      // 첫 점은 M, 나머지는 L. 소수점 2자리로 줄여 path를 가볍게.
      return `${i === 0 ? 'M' : 'L'}${x.toFixed(2)} ${y.toFixed(2)}`;
    })
    .join(' ')
    .concat(' Z');
}
```

MultiPolygon은 서브 경로가 여러 개라는 점만 다릅니다. 각 링을 path 문자열로 만든 뒤 공백으로 이어 붙이면, 하나의 `<path>` 안에 여러 도형이 함께 그려집니다. 각 링은 `M ... Z`로 끝나므로 이어 붙이면 `M ... Z M ... Z` 형태가 되는데, SVG는 `M`이 나올 때마다 새 서브패스(도형)로 인식합니다.

이 방식에는 전제가 하나 있습니다. 구멍(내부 링)이 뚫리려면 구멍 링이 바깥 링과 **반대 방향으로 감겨(winding)** 있어야 합니다. 바깥 링을 반시계로 그렸다면 구멍 링은 시계처럼 서로 반대로 그려야 SVG가 안쪽을 구멍으로 인식하고, 둘이 같은 방향이면 구멍까지 모두 칠해집니다.

이는 SVG의 기본 `fill-rule`인 `nonzero`가 감김 방향으로 안팎을 판정하기 때문입니다. GeoJSON 표준(RFC 7946)도 바깥 링과 구멍 링을 반대 방향으로 감도록 정해두고 있습니다. 다만 구멍이 뚫리는 조건은 RFC 준수 여부가 아니라 **바깥과 구멍이 서로 반대로만 감겨 있는지**입니다(실제 방향은 데이터마다 다를 수 있습니다). 방향을 신경 쓰고 싶지 않다면 `<path>`에 `fill-rule="evenodd"`를 주면 됩니다. 감김 방향과 상관없이 교차 횟수로 안팎을 판정하니 더 안전합니다. 이 글의 시도 데이터에는 호수 같은 구멍이 거의 없어 어느 쪽이든 결과는 같습니다.

```js
function featureToPath(feature, project) {
  const d = extractPolygons(feature.geometry)
    .flatMap((polygon) => polygon.map((ring) => ringToPath(ring, project)))
    .join(' ');

  const path = document.createElementNS('http://www.w3.org/2000/svg', 'path');
  path.setAttribute('d', d);
  path.setAttribute('class', 'region');
  // 지역명을 data 속성에 담아 hover/클릭에서 꺼내 쓴다.
  path.dataset.name = feature.properties.name ?? '';
  return path;
}
```

`<path>`를 만들 때는 `createElement`가 아니라 `createElementNS`를 써야 합니다. SVG 요소는 일반 HTML과 달리 네임스페이스를 지정해 만들어야 합니다. `document.createElement('path')`로 만들면 화면에 아무것도 그려지지 않는 흔한 문제가 생깁니다.

`properties.name`을 `data-name` 속성에 저장해두면, 이벤트 핸들러에서 별도 조회 없이 어느 지역인지 알 수 있습니다.

마지막으로 모든 Feature를 순회해 `<svg>`에 붙이면 지도가 완성됩니다.

```js
export function renderMap(geojson, { width = 720, height = 820, padding = 28 } = {}) {
  const svg = document.createElementNS('http://www.w3.org/2000/svg', 'svg');
  svg.setAttribute('viewBox', `0 0 ${width} ${height}`);

  const bounds = computeBounds(geojson.features);
  const project = createProjector(bounds, width, height, padding);

  for (const feature of geojson.features) {
    svg.appendChild(featureToPath(feature, project));
  }
  return svg;
}
```

지도를 그리는 과정은 bounding box 계산, 투영, path 변환의 세 단계입니다.

이제 GeoJSON을 불러와 화면에 붙이기만 하면 됩니다. `fetch`로 `.json`을 읽어 `renderMap`에 넘기고, 반환된 `<svg>`를 문서에 끼워 넣습니다.

```js
const res = await fetch('/korea-sido.json'); // GeoJSON 파일을 불러온다.
const geojson = await res.json(); // 그냥 JSON이라 별도 파서 없이 파싱된다.

const svg = renderMap(geojson); // 위에서 만든 함수로 SVG를 만든다.
document.querySelector('#app').appendChild(svg); // 문서에 붙이면 화면에 나타난다.
```

한 가지 실행 전제가 있습니다. 위 `await fetch(...)`는 최상위 `await`라 `<script type="module">`에서만 동작하고, `index.html`을 `file://`로 그냥 열면 `fetch`가 CORS로 막힙니다. `vite`나 `npx serve` 같은 로컬 서버로 띄워야 합니다.

## 4단계: hover로 지역 강조하기

지도가 그려졌으니 약간의 상호작용을 더해봅니다. 마우스를 올린 지역의 색을 바꾸고, 이름을 화면에 띄우는 정도로 충분합니다.

지역이 17개뿐이라 path마다 리스너를 다는 것도 가능하지만, 여기서는 SVG 하나에만 리스너를 달고 이벤트 위임으로 처리합니다. 이벤트 위임은 부모 하나에 리스너를 달아두고, 이벤트가 자식에서 부모로 버블링되는 성질을 이용해 `e.target`으로 실제 대상을 가려내는 기법입니다. path가 수백 개로 늘어나도 리스너는 하나면 됩니다.

한 가지 주의할 점은 `mouseenter`/`mouseleave`가 아니라 `mouseover`/`mouseout`을 써야 한다는 것입니다. `mouseenter`/`mouseleave`는 버블링되지 않아 위임이 동작하지 않습니다.

```js
svg.addEventListener('mouseover', (e) => {
  const target = e.target;
  if (!(target instanceof SVGPathElement)) return;
  // hover한 지역에 강조 클래스를 붙여 채움색을 바꾼다.
  target.classList.add('is-active');
  label.textContent = target.dataset.name ?? '';
});

svg.addEventListener('mouseout', (e) => {
  const target = e.target;
  if (!(target instanceof SVGPathElement)) return;
  target.classList.remove('is-active');
});
```

`e.target instanceof SVGPathElement` 가드는 SVG 자체나 path가 아닌 다른 요소 위로 마우스가 지나갈 때를 걸러내기 위한 것입니다. 위임이다 보니 path가 아닌 곳에서도 이벤트가 잡히는데, 그런 경우엔 그냥 무시하면 됩니다.

색을 바꾸는 일은 CSS에 맡깁니다. JavaScript는 클래스만 토글하고, 실제 스타일은 `.region`과 `.is-active`로 분리해두면 코드 구조가 단순해집니다.

```css
.region {
  fill: #dbeafe;
  stroke: #60a5fa;
  stroke-width: 0.8;
  transition: fill 0.12s ease;
  cursor: pointer;
}
.region.is-active {
  fill: #f59e0b; /* hover 시 주황색으로 강조 */
}
```

`data-name`에 지역명을 미리 넣어둔 덕분에, 이벤트 핸들러는 `target.dataset.name`만 읽으면 됩니다. 결과는 이렇습니다.

![경상북도에 마우스를 올려 강조된 지도. 부속 섬 울릉도까지 함께 강조되고 지역명이 표시된다](/geojson-hover.png)

경상북도에 마우스를 올리니 본토뿐 아니라 동쪽의 울릉도까지 함께 강조됩니다. 두 도형이 하나의 MultiPolygon이라서, 앞에서 지역마다 만든 `<path>` 하나에 함께 들어 있기 때문입니다.

## 정리

라이브러리 없이 GeoJSON을 지도로 그리는 과정은 다음과 같습니다.

- GeoJSON은 그냥 JSON이고, 좌표는 `[경도, 위도]` 순서다. Polygon과 MultiPolygon만 알면 지도 대부분을 그릴 수 있다.
- 모든 좌표를 훑어 bounding box를 구하고, 그걸 화면 크기에 맞춰 스케일·정렬한다.
- 투영은 x와 y를 같은 공간(메르카토르)에서 계산해 스케일을 맞춰야 한다. 스케일이 어긋나면 지도가 찌부러진다.
- 화면 y축은 아래로 커지므로 위도를 뒤집어야 북쪽이 위로 간다.
- 각 도형을 `M`/`L`/`Z` 문법의 SVG path로 바꾸고, `data` 속성과 이벤트 위임으로 상호작용을 붙인다.

## 마치며

라이브러리 없이 직접 구현해 보면, 평소 한 줄로 쓰던 지도 라이브러리가 내부에서 어떤 일을 하는지 알 수 있습니다. 좌표를 픽셀로 옮기는 투영, 비율을 지키는 스케일링, 위아래를 뒤집는 부호 처리처럼 자잘하지만 틀리기 쉬운 계산을 라이브러리가 대신 처리해줍니다.

실무에서는 leaflet이나 d3 같은 라이브러리를 쓰는 편이 낫습니다. 줌, 타일, 좌표계 변환까지 직접 만들 필요는 없습니다. 원리를 알고 나면 이런 도구가 제공하는 옵션 이름이나 에러 메시지를 더 쉽게 이해할 수 있습니다.

`playground/geojson-viz`의 예제 코드에 다른 나라나 도시의 GeoJSON을 넣으면, 데이터만 바꿔도 같은 투영·스케일링 코드가 그대로 동작합니다.
