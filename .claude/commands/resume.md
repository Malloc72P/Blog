입력값: $ARGUMENTS

입력값으로 받은 작업문서폴더를 기준으로, 다른 세션이 `/start` 로 진행하다 멈춘 작업을 이어서 한다.
입력값이 없으면 아래 「인자」대로 폴더를 찾는다.

이 커맨드는 두 부분으로 되어 있다. 앞부분은 **재개 준비**로, 산출물과 코드를 읽어 지금 어느
단계인지 판정하고 보고한 뒤 멈춘다. 뒷부분은 **이후 단계**로, `/start` 와 같은 절차와 규칙을 따른다.

## 인자

- 작업문서폴더는 `docs/tasks/` 밑의 폴더다. `35-decorator-metadata` 처럼 이름만 줘도 되고
  `docs/tasks/35-decorator-metadata` 처럼 경로로 줘도 된다.
- 생략하면 브랜치 이름에서 슬러그를 뽑아 찾는다. 뽑는 방법은 `/start` 의 "작업문서폴더를 만든다"
  와 같다. `docs/tasks/` 에서 `<번호>-<슬러그>` 또는 `<슬러그>` 폴더를 고른다.
- 폴더가 없거나 둘 이상 걸리면 `docs/tasks/` 의 폴더 목록을 보여주고 사용자에게 묻는다. 브랜치
  이름에서 슬러그를 뽑을 수 없을 때(자동 이름, 이슈 번호가 여럿)도 같다. 새로 만들지 않는다.
  폴더를 새로 만드는 것은 `/start` 의 일이다.
- 현재 브랜치의 슬러그가 작업문서폴더의 슬러그와 다르면 체크아웃이나 워크트리 생성을 하지 않고
  사용자에게 알린다. 그 상태로 진행할지는 사용자가 정한다.

## 재개 준비

아래 순서로 읽는다. 읽는 동안 코드·문서·원격을 바꾸지 않는다. 바꾸는 것은 마지막의
`temp-memory.md` 재개 기록 추가 하나뿐이다.

1. **`temp-memory.md`** — 되돌릴 임시 조작과 개발 단계의 작업 체크리스트를 읽는다. 산출물에 안
   적힌 임시 상태가 여기 있다. 프론트매터의 `stage`·`round`·`status` 도 읽는다. `status: 진행중`
   이면 그 단계를 하던 중에 멈춘 것이다. 아래 판정 표의 결과와 다르면 산출물과 코드 쪽을 믿고,
   어긋난 것을 보고에 적는다.
2. **`NN-*.md` 산출물 전부, 연번 순서로** — 01 부터 마지막까지 빠짐없이 읽는다. 각 산출물이 어느
   단계의 것인지(원인분석·요구사항분석·계획·N차완료·N차리뷰및개선·자유 이름) 적어 둔다. "남은 것"
   처럼 남은 일이나 정하지 못한 것을 적은 절이 있으면 그 내용도 적어 둔다.
3. **이슈** — 폴더 이름에 이슈 번호가 있으면 `gh issue view <번호> --comments` 로 상태와 코멘트를
   읽는다. 마지막 산출물 날짜 뒤에 달린 코멘트가 있으면 새 지시일 수 있으니 따로 적는다.
4. **PR** — `gh pr list --head <브랜치> --state all` 로 PR 과 그 상태(열림·병합·닫힘)를 본다.
   `--state all` 을 빼면 열린 PR 만 나와, 병합된 작업을 "PR 없음"으로 잘못 본다. PR 이 있으면
   `gh pr view <번호> --comments` 와 `gh api repos/{owner}/{repo}/pulls/<번호>/comments` 로 리뷰
   코멘트를 읽고, 산출물이나 코드에 아직 반영되지 않은 것을 가려낸다.
5. **git 상태** — 아래 셋을 본다.
   - `git status` — 미커밋 변경. 산출물에 없는 변경이면 무엇인지 파악한다.
   - `git log -1 --format=%h -- <마지막 산출물 경로>` 로 마지막 산출물이 들어간 커밋을 찾고,
     `git log --oneline <그 커밋>..HEAD` 로 그 뒤에 들어온 커밋을 읽는다. 이 커밋들이 **문서에
     기록되지 않은 작업**이다. 마지막 산출물이 아직 커밋되지 않았으면 그렇게 적고, 브랜치의 커밋
     전체(`git log --oneline main..HEAD`)를 문서에 기록되지 않은 작업의 후보로 본다.
   - `git diff main...HEAD --stat` — 브랜치 전체에서 바뀐 파일 목록. 산출물이 언급한 파일과
     대조한다.
6. **관련 코드** — 마지막 두 산출물이 다룬 파일을 전부 읽는다. 마지막 산출물이 계획 문서면 그
   작업 순서 항목 하나하나를 코드와 `temp-memory.md` 체크리스트에 대조해 끝난 항목과 남은 항목을
   가른다. 체크리스트나 작업별 검증 명령이 없는 폴더면 코드와 테스트를 직접 읽어 가르고, 근거가
   약하다고 보고에 적는다. 산출물 뒤에 들어온 커밋이 있으면 그 diff 도 읽는다.
7. **테스트** — 브랜치에 코드 변경이 있으면 `pnpm --filter blog test` 를 한 번 돌려 테스트 수와
   통과 여부를 적는다. 마지막 산출물에 적힌 수와 다르면 그 차이를 기록한다.
8. **되돌릴 것 점검** — `temp-memory.md` 의 되돌릴 것이 지금도 그 상태인지 확인한다. 이미
   되돌려져 있으면 그렇다고 적고, 되돌리지는 않는다.

## 현재 단계 판정

마지막 산출물의 종류와 그 뒤의 상태로 판정한다. 위에서부터 처음 맞는 줄을 쓴다. 맞는 줄이 없으면
판정하지 말고 사용자에게 묻는다.

표의 "코드 변경"은 마지막 산출물 뒤에 생긴 소스·테스트 파일의 변경이다. 커밋과 미커밋을 모두
센다. 작업문서폴더의 문서는 세지 않는다.

| 마지막 산출물 | 그 뒤의 상태 | 판정 |
| --- | --- | --- |
| 무엇이든 | PR 이 병합됨 | 작업이 끝났다. 되돌릴 것이 남았는지만 보고한다 |
| 무엇이든 | PR 이 병합 없이 닫힘 | 이어갈지 사용자에게 묻는다 |
| 없음(`temp-memory.md` 만 있음) | — | 원인 분석 또는 요구사항 분석 차례 |
| 원인분석 · 요구사항분석 | — | 계획 차례 |
| 계획, 또는 자유 이름의 계획 문서 | 코드 변경 없음 | 개발 차례 |
| 계획, 또는 자유 이름의 계획 문서 | 코드 변경 있음 | 개발 진행 중. 작업 순서와 코드를 대조해 남은 항목을 가른다. 남은 항목이 없으면 완료 문서 작성 차례 |
| N차완료 · N차리뷰및개선 | 코드 변경 있음 | 문서에 없는 작업이 있다. 무엇인지 파악해 보고하고, 어느 산출물에 담을지 사용자에게 묻는다 |
| N차완료 | 코드 변경 없음 | 리뷰 및 개선 차례 |
| N차리뷰및개선 | 열린 PR 없음 | 다음 회차 리뷰 및 개선 또는 PR 리뷰 차례. 어느 쪽인지는 사용자가 정한다 |
| N차리뷰및개선 | 열린 PR 있음 | PR 리뷰 진행 중. PR 본문에 체크리스트 대조 결과가 있는지 본다. 미반영 PR 코멘트가 있으면 그 반영이 먼저다 |
| 계획이 아닌 자유 이름 문서 | — | 내용을 읽고 위 표에 맞춰 판정한다. 확신이 없으면 묻는다 |

이 표는 재개 준비에서 지금 단계를 판정할 때만 쓴다. 재개 뒤 다음 단계는 `/start` 의 단계 순서를
따른다.

판정 근거를 한 줄로 적는다 — "마지막 산출물 `02-계획.md` 뒤에 커밋이 두 개 있고 완료 문서가 없어
개발 진행 중으로 본다".

다음 산출물의 이름도 여기서 정한다. 연번은 폴더 안에서 가장 큰 `NN` 에 1을 더하고, 완료·리뷰
회차는 각각 마지막 `N차완료`·`N차리뷰및개선` 의 N에 1을 더한다(없으면 1차, 둘은 따로 센다). 파일
이름 형식과 이 계산 방법은 `write-deliverable` 스킬의 파일 이름 규칙과 같다.

## 재개 기록

`temp-memory.md` 끝에 아래 절을 덧붙인다. 재개 준비 중에는 앞의 내용을 지우거나 고치지 않는다.

```markdown
## 재개 (YYYY-MM-DD)

- 읽은 산출물: 01 ~ NN
- 브랜치·HEAD: `<브랜치>`, `<HEAD>`
- PR: <번호와 상태, 없으면 "없음">
- 마지막 산출물 뒤 커밋: <목록, 없으면 "없음">
- 미커밋 변경: <목록, 없으면 "없음">
- 테스트: <테스트 수, 통과 여부. 코드 변경이 없어 안 돌렸으면 그렇게>
- 현재 단계 판정: <판정> — <근거 한 줄>
- 문서와 코드가 어긋난 것: <목록, 없으면 "없음">
- 미반영 이슈·PR 코멘트: <목록, 없으면 "없음">
- 되돌릴 것 중 남은 것: <목록, 없으면 "없음">
- 다음 산출물: `NN-이름.md`
```

## 보고하고 멈춘다

재개 기록을 쓴 뒤 사용자에게 보고한다. 앞 세션의 대화를 모르는 사람이 읽어도 되게, 이슈가
무엇이고 어디까지 왔고 무엇이 남았는지부터 쓴다. 문서와 코드가 어긋난 것과 미반영 코멘트는
빠짐없이 적는다.

보고의 마지막은 "다음 단계로 <판정한 단계> 를 진행할까요?" 하나로 끝낸다. **다음 단계는 사용자의
명시적인 지시가 있을 때만 시작한다.** 재개 준비를 마쳤다고 바로 코드를 고치거나 산출물을 만들지
않는다.

## 이후 단계

재개 준비를 마치면 `.claude/commands/start.md` 를 읽는다. 이후 단계의 절차와 규칙은 그 파일의
「작업 프로세스」·「리뷰 지적 다루기」·「승인 규칙」 절을 그대로 따른다. 각 단계와 커밋·푸시는
`/start` 처럼 사용자 지시가 있을 때만 한다. 산출물도 `/start` 처럼 `write-deliverable` 스킬로 쓴다.
규칙을 여기에 옮겨 적지 않는다. 한 곳만 고치면 되게 하려는 것이다.

`/start` 와 다른 점만 아래에 적는다.

- 작업문서폴더와 `temp-memory.md` 를 새로 만들지 않는다. 있는 것을 쓴다.
- 산출물 연번과 회차는 [현재 단계 판정](#현재-단계-판정) 에서 정한 값으로 이어 받는다. 01 부터
  다시 시작하지 않는다.
- 이미 있는 `NN-*.md` 중 끝난 단계의 문서는 한 글자도 고치지 않는다. 앞 세션이 쓴 산출물에 틀린
  것이 보여도 그렇다. 바로잡을 내용은 새 산출물에 적는다(`write-deliverable` 의 수정 금지 규칙과
  같다).
- 새 산출물의 첫 줄에는 어느 산출물의 뒤를 잇는지 링크로 적는다 — "[02-계획.md](02-계획.md) 의
  작업 순서 1~4 를 마쳤다".
- 재개 뒤에 임시로 기록할 것이 생기면 `temp-memory.md` 의 재개 절 아래에 이어 적는다. 작업
  체크리스트는 `/start` 3단계대로 체크한다.
