지시받은 이슈를 아래 작업 프로세스대로 처리한다. 대상은 블로그 앱(`apps/blog`)의 기능 구현과
유지보수다. 포스트 작성은 이 커맨드가 아니라 `/blog-post`·`/blog-from-notion` 이 맡는다.

## 시작하기 전에

**작업문서폴더를 만든다** — `docs/tasks/<이슈번호>-<영문슬러그>/`. 이미지는 그 밑 `images/` 에 둔다.
이 폴더의 문서는 git 에 함께 커밋한다.

**`temp-memory.md` 를 만든다.** 작업 도중 되돌려야 할 임시 조작을 여기 적는다. 다른 세션이 3000
포트를 쓰고 있어 개발 서버를 다른 포트로 띄웠다면, 마무리에 되돌릴 수 있게 적어두는 식이다. 이
파일만 예외로 계속 고쳐 쓴다.

**첫 단계를 정한다.** `gh issue view <번호> --json labels` 로 라벨을 읽는다.

| 라벨 | 첫 단계 |
| --- | --- |
| `bug` | 원인 분석 |
| `enhancement` · `documentation` | 요구사항 분석 |
| `blog-post` · `idea` | 포스트 주제 아이디어다. 이 커맨드 대상이 아니라고 알리고 멈춘다 |
| `보류` | 진행하지 않기로 한 이슈다. 진행할지 사용자에게 먼저 묻는다 |
| 없음 | 사용자에게 묻는다 |

판정 근거를 첫 산출물의 첫 줄에 적는다 — "이 이슈는 `bug` 라벨이라 원인 분석으로 진행한다".

## 작업 프로세스

### 1단계. 원인 분석 / 요구사항 분석

버그면 `01-원인분석.md`, 그 밖이면 `01-요구사항분석.md` 를 쓴다.

**원인 분석은 재현이 필수다.** `.claude/launch.json` 의 `blog` 설정으로 개발 서버를 띄우고
브라우저에서 재현한 뒤 **화면 이미지를 산출물에 첨부한다.** 코드만 읽고 원인을 추정하지 않는다.
재현 환경(URL·뷰포트 크기·다크모드 여부·브라우저)도 함께 적어, 나중에 같은 자리에서 다시 돌릴 수
있게 한다. 반응형 문제면 재현한 뷰포트 폭을 숫자로 적는다.

**요구사항 분석에는** 무엇을 만드는지, 왜 필요한지, 어느 라우트·컴포넌트가 바뀌는지, 기존 포스트
MDX 렌더에 영향이 있는지를 적는다.

### 2단계. 계획

`02-계획.md` 를 쓴다. 세 가지를 담는다.

- **방향** — 후보를 몇 개 놓고 무엇으로 갈지 고른다. **버린 대안과 그 이유를 함께 적는다.** 코드는
  지금 무엇을 하는지 알려주지만 무엇을 해봤다가 실패했는지는 못 알려준다. 실측한 수치가 있으면
  같이 적고 어디서 쟀는지도 남긴다.
- **검증** — 단위 테스트와 e2e 로 무엇을 어떻게 확인할지.
- **완료 조건 체크리스트** — 아래 표를 채운다.

| 항목 | 판단 기준 |
| --- | --- |
| 구현 | 항상 |
| 단위 테스트 (Jest) | 항상 |
| e2e (Playwright) | 화면으로 확인되는 변경이면 |
| 브라우저 확인 | 눈으로 확인할 게 있나 |
| 반응형 · 다크모드 | UI 변경이면 |
| 접근성 | 상호작용 요소나 포커스 흐름이 바뀌나 |
| 기존 포스트 MDX | 포스트 렌더 결과가 바뀌나 |
| 문서 갱신 | CLAUDE.md · README 의 규칙이나 구조가 바뀌나 |

각 항목에 "필요 / 불필요"와 근거 한 줄을 단다.

### 3단계. 개발

구현하고 `03-1차완료.md` 에 무엇을 어떻게 했는지 적는다. 파일별 변경 표와 테스트 결과를 담는다.

**CLAUDE.md 의 코딩 규칙을 지킨다** — `any` 지양, non-null assertion(`!`) 금지, `object possibly
undefined` 가 나지 않도록 타입 가드 작성.

검증은 CI 와 같은 순서로 로컬에서 돌린다.

```bash
pnpm --filter blog lint
pnpm --filter blog exec tsc --noEmit
pnpm --filter blog test
pnpm --filter blog test:e2e
```

범위가 늘어 다시 구현했으면 `NN-2차완료.md` 를 새로 만든다. 1차 완료 문서는 고치지 않는다.

### 4단계. 리뷰 및 개선

자가 리뷰를 하고 `NN-1차리뷰및개선.md` 에 적는다. 회차마다 새 문서를 만든다.

**리뷰에서 방향이 뒤집히면 무엇을 왜 바꿨는지 이 문서에 적는다.** 2단계 계획 문서는 고치지 않는다.

### 5단계. PR 리뷰

draft PR 을 올리고 `/reviewbeta` 로 보고서 아티팩트를 만든다.

**2단계의 완료 조건 체크리스트를 여기서 대조한다.** 필요하다고 적은 항목이 전부 들어갔는지
확인하고 결과를 PR 본문에 적는다.

## 산출물 규칙

**파일명은 `NN-단계이름.md`** 다. 두 자리 연번을 쓰고, 단계 이름은 `원인분석`·`요구사항분석`·
`계획`·`N차완료`·`N차리뷰및개선` 중에서 고른다. 예정에 없던 문서가 중간에 필요하면 다음 연번을
받고, 이때만 이름을 자유롭게 짓는다.

**끝난 단계의 문서는 고치지 않는다.** 결정이 번복되면 이전 문서를 고치는 대신 다음 연번 문서에 새
내용을 적는다. 리뷰 내용이 뒤집히는 경우도 다음 회차 문서에 적는다. 예외는 `temp-memory.md` 하나다.

**코드가 작업 문서를 가리키지 않는다.** 작업 문서는 그때 그랬다는 기록이라 지금도 유효한지를
말하지 않는다. 반대 방향, 작업 문서가 코드 파일을 가리키는 것은 괜찮다.

**모든 마크다운 산출물과 PR 본문은 `/refine-korean` 과 korean-concise 로 다듬는다.**

## 승인 규칙

- **각 단계는 사용자의 명시적인 지시가 있을 때만 시작한다.**
- 어느 단계에서든 커밋과 푸시는 사용자의 명시적인 지시가 있을 때만 한다.
- GitHub PR 을 한 번 만들고 나면, 그 PR 에 대한 수정도 사용자의 명시적인 지시가 있을 때만 한다.
- reviewbeta 로 만든 보고서 아티팩트도 한 번 만들고 나면, 그에 대한 수정은 사용자의 명시적인
  지시가 있을 때만 한다.
