지시받은 이슈를 아래 작업 프로세스대로 처리한다. 대상은 블로그 앱(`apps/blog`)의 기능 구현과
유지보수다. 포스트 작성은 이 커맨드가 아니라 `/blog-post`·`/blog-from-notion` 이 맡는다.

이 커맨드는 진행 순서와 규칙만 정한다. 작업문서폴더의 산출물에 무엇을 담고 어떻게 쓰는지는
`write-deliverable` 스킬이 정한다. 중단된 작업은 `/resume` 으로 이어간다.

## 시작하기 전에

**작업문서폴더를 만든다** — `docs/tasks/<이슈번호>-<슬러그>/`. 이미지는 그 밑 `images/` 에 둔다.
이 폴더의 문서는 git 에 함께 커밋한다.

- 슬러그는 **브랜치 이름에서 가져온다.** 첫 `/` 앞의 접두어(`claude/`·`malloc72p/`·`fix/` 등)를
  떼고, 이어지는 `issue-<번호>-` 도 뗀다. 끝에 워크트리 해시(`-` 뒤 6자리 16진수)가 붙었으면
  그것도 뗀다. `claude/issue-35-decorator-metadata` 이면 `decorator-metadata` 다. 이슈 제목에서
  지어내면 매번 다른 이름이 나오고, `/resume` 이 폴더를 찾지 못한다.
- 브랜치 이름이 이슈와 관계없는 자동 이름(`claude/zen-antonelli-71a5f7` 같은)이거나 이슈 번호가
  여럿 들어 있으면, 슬러그를 지어내지 말고 사용자에게 묻는다.
- 이슈 없이 시작한 작업은 번호를 빼고 슬러그만 쓴다.

**작업문서폴더에 `temp-memory.md` 를 만든다.** 작업 도중 되돌려야 할 임시 조작을 여기 적는다.
다른 세션이 3000 포트를 쓰고 있어 개발 서버를 다른 포트로 띄웠다면, 마무리에 되돌릴 수 있게
적어두는 식이다. 개발 단계의 작업 체크리스트도 여기에 둔다(3단계). `temp-memory.md` 변경도
작업문서폴더의 다른 문서와 함께 커밋한다.

**첫 단계를 정한다.** `gh issue view <번호> --json labels` 로 라벨을 읽는다.

| 라벨 | 첫 단계 |
| --- | --- |
| `bug` | 원인 분석 |
| `enhancement` · `documentation` | 요구사항 분석 |
| `blog-post` · `idea` | 포스트 주제 아이디어다. 이 커맨드 대상이 아니라고 알리고 멈춘다 |
| `보류` | 진행하지 않기로 한 이슈다. 진행할지 사용자에게 먼저 묻는다 |
| 없음 | 사용자에게 묻는다 |

판정 근거는 첫 산출물의 첫 줄에 적는다.

## 작업 프로세스

원인 분석(버그) 또는 요구사항 분석 → 계획 → 개발 → 리뷰 및 개선(반복) → PR 리뷰 순서로 진행한다.
각 단계가 끝나면 그 단계의 산출물을 `write-deliverable` 스킬로 작업문서폴더에 남긴다.

각 단계의 변경분은 다음 단계로 넘어가기 전에 커밋한다. 사용자가 다음 단계로 진행하라고 지시하면,
다음 단계를 시작하기 전에 이전 단계의 변경분을 먼저 커밋한다.

### 1단계. 원인 분석 / 요구사항 분석

버그면 원인 분석, 그 밖이면 요구사항 분석을 한다.

**원인 분석은 재현이 필수다.** `.claude/launch.json` 의 `blog` 설정으로 개발 서버를 띄우고
브라우저에서 재현한다. 코드만 읽고 원인을 추정하지 않는다.

### 2단계. 계획

방향, 작업 순서, 검증 방법, 완료 조건 체크리스트를 정한다.

### 3단계. 개발

계획의 작업 순서를 `temp-memory.md` 에 체크리스트로 옮겨 적는다. 작업을 하나씩 구현하고, 그
작업의 검증 명령으로 기대 결과를 확인할 때마다 체크한다. 세션이 끊겼다가 이어서 할 때는 이
체크리스트와 각 작업의 검증 명령으로 어디까지 했는지 확인한다. 구현 중 계획이 바뀌면 바뀐 내용을
산출물로 먼저 남기고, 체크리스트도 거기에 맞춰 고친다.

**버그면 재현 테스트부터 쓴다.** 1단계에서 재현한 증상을 테스트로 옮기고, 그 테스트가 실패하는
것을 확인한 뒤 고치기 시작한다. 테스트로 고정할 수 없는 버그면 계획에 그 이유를 적고 사용자에게
알린다.

**CLAUDE.md 의 코딩 규칙을 지킨다** — `any` 지양, non-null assertion(`!`) 금지, `object possibly
undefined` 가 나지 않도록 타입 가드 작성.

**코드가 작업 문서를 가리키지 않는다.** 작업 문서는 그때 그랬다는 기록이라 지금도 유효한지를
말하지 않는다. 반대 방향, 작업 문서가 코드 파일을 가리키는 것은 괜찮다.

구현을 마치면 CI 와 같은 순서로 로컬에서 검증한다.

```bash
pnpm --filter blog lint
pnpm --filter blog exec tsc --noEmit
pnpm --filter blog test
pnpm --filter blog test:e2e
```

범위가 늘어 다시 구현했으면 다음 회차 완료 산출물을 새로 쓴다.

### 4단계. 리뷰 및 개선

자가 리뷰를 하고 리뷰 및 개선 산출물을 쓴다. 회차마다 새 문서를 만든다.

### 5단계. PR 리뷰

draft PR 을 올린다.

**2단계의 완료 조건 체크리스트를 여기서 대조한다.** 필요하다고 적은 항목이 전부 들어갔는지
확인하고 결과를 PR 본문에 적는다. PR 본문은 `write-deliverable` 스킬로 쓴다.

## 리뷰 지적 다루기

리뷰 지적(자가 리뷰, PR 리뷰)은 바로 반영하지 않는다. 지적이 실제 코드와 맞는지 먼저
확인한다. 이해가 안 되는 항목이 하나라도 있으면 어느 항목도 고치지 말고 먼저 묻는다.

## 승인 규칙

- **각 단계는 사용자의 명시적인 지시가 있을 때만 시작한다.**
- 어느 단계에서든 커밋과 푸시는 사용자의 명시적인 지시가 있을 때만 한다. 단, 다음 단계를 진행하라는
  지시를 받으면 이전 단계의 변경분을 커밋하는 것은 예외로 허용한다.
- GitHub PR 을 한 번 만들고 나면, 그 PR 에 대한 수정도 사용자의 명시적인 지시가 있을 때만 한다.
