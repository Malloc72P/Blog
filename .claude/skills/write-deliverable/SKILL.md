# 무엇을 하는 스킬인가

`/start`·`/resume` 작업 프로세스에서 각 단계가 끝날 때마다 작업문서폴더
(`docs/tasks/<이슈번호>-<슬러그>/`) 밑에 남기는 마크다운 산출물을 작성한다.
원인분석·요구사항분석·계획·N차완료·N차리뷰및개선 산출물과, PR 리뷰 단계의 PR 본문이 대상이다.

이 스킬은 산출물의 **형식, 단계별로 담을 내용, 다듬기**를 책임진다. 무엇을 조사했고 무엇을
결정했는지는 호출한 쪽(`/start`·`/resume` 을 진행하는 세션)이 이미 파악해서 넘겨준다.

# 항상 Sonnet으로 작성한다

이 스킬이 호출되면 실제 파일 작성은 직접 하지 않고 Agent 도구로 위임한다.

```
Agent({
  subagent_type: "general-purpose",
  model: "sonnet",
  prompt: "<아래 내용을 채워 전달>"
})
```

`model` 에는 버전 번호 없이 `"sonnet"` 별칭만 넣는다. 이 별칭은 호출하는 시점의 가장 최신
Sonnet을 가리킨다.

프롬프트에 담을 것:

- 작업문서폴더 경로 (워크트리에서 작업 중이면 워크트리의 절대경로)
- 어느 단계인지 (원인분석 / 요구사항분석 / 계획 / N차완료 / N차리뷰및개선 / PR 본문 / 자유 이름)
- 파일 이름 — 연번까지 정해서 넘긴다. 정하는 방법은 [파일 이름 규칙](#파일-이름-규칙) 참고
- 담을 내용 — 호출한 세션이 조사·결정한 사실을 정리해서 넘긴다. 조사를 다시 시키지 않는다
- 이 SKILL.md 전체 — 서브에이전트가 형식·다듬기 규칙을 스스로 확인하며 쓰게 한다
- 직접 쓰라는 지시 — 받는 쪽은 이미 위임받은 서브에이전트다. 이 스킬을 다시 부르거나 다른
  에이전트에 위임하지 말고 파일을 직접 쓰게 한다

호출한 세션이 지금 어떤 모델로 돌고 있는지와 무관하게, 산출물 텍스트는 항상 이 방식으로
Sonnet이 쓴다.

# 파일 이름 규칙

- `NN-단계이름.md` 형식. 두 자리 연번을 쓴다.
- 단계 이름은 `원인분석`·`요구사항분석`·`계획`·`N차완료`·`N차리뷰및개선` 중에서 고른다. N 은
  완료·리뷰 각각 따로 센다.
- 연번은 폴더 안 가장 큰 `NN` 에 1을 더한다.
- 예정에 없던 문서가 중간에 필요하면 다음 연번을 받고, 이때만 이름을 자유롭게 짓는다.
- 이미지는 작업문서폴더 밑 `images/` 에 두고 상대 경로로 링크한다.

# 산출물 쓰는 법

**쉽고 짧게 쓰되 빠뜨리지 않는다.** 산출물은 나중에 다른 사람이 읽고 바로 이해할 수 있어야 한다.

- 첫 줄에 판정 근거나 앞 문서와의 관계를 적는다 — "이 이슈는 `bug` 라벨이라 원인 분석으로
  진행한다", "[02-계획.md](02-계획.md) 의 작업 1~4 를 마쳤다".
- 그 아래에 세 줄 안팎의 요약을 둔다. 결론과 판단이 먼저 오고 근거는 뒤에 온다.
- 절 하나는 문단 1~3개로 끝낸다. 근거·측정값·선택지 비교는 줄글 대신 표나 목록으로 쓴다.
- 내부 컴포넌트·함수 이름은 꼭 필요할 때만 쓴다. 쓸 때는 처음 나오는 자리에서 무엇을 하는
  것인지 한 줄로 풀어 쓴다.
- 코드 블록과 계산식은 그게 없으면 뜻이 통하지 않을 때만 넣고, 넣더라도 필요한 줄만 자른다.
- **짧게 만들려고 결정한 것·측정값·확인한 사실을 지우지 않는다.** 문서가 길어지면 이것들을
  덜어내지 말고, 덜 중요한 배경 설명과 중간 과정을 덜어낸다.

**이어받는 사람을 위해 남길 것.** 짧게 쓴다는 것은 설명 문장을 줄인다는 뜻이지 사실을 줄인다는
뜻이 아니다. 아래는 코드를 읽어도 나오지 않고 문서에만 있는 것이라, 빠지면 다음 사람이 처음부터
다시 조사해야 한다.

- **어디를 봐야 하는지** — 다룬 파일 경로와 컴포넌트·함수 이름. 코드를 열면 보이는 설명은
  줄이되, 어느 파일의 무엇인지는 반드시 적는다.
- **어떻게 재현하고 측정했는지** — 연 URL, 실행한 명령, 측정 조건(뷰포트 크기, 다크모드 여부,
  브라우저). 스크립트를 썼으면 파일을 첨부하지 않고, 그 스크립트로 무엇을 어떻게 확인했는지 몇 줄로
  적는다. 출력도 로그 파일로 첨부하지 않고, 결론을 뒷받침하는 줄만 본문에 붙인다.
- **버린 대안과 버린 이유** — 검토했다가 쓰지 않기로 한 방법. 이유를 적지 않으면 다음 사람이
  같은 길을 다시 판다.
- **아직 정하지 못한 것과 확인하지 못한 것** — 남은 결정과 그 선택지, 확인하지 못한 것.

# 단계별로 담을 것

아래 표의 내용과 위 「이어받는 사람을 위해 남길 것」을 담고, 나머지는 덜어낸다.

| 단계 | 담을 것 |
| --- | --- |
| 원인분석 | 무엇이 어떻게 잘못됐는지, 원인이 무엇인지, 어떻게 재현했는지(화면 이미지 첨부), 재현 환경, 원래부터 있던 문제인지 |
| 요구사항분석 | 무엇을 만드는지, 왜 필요한지, 어느 라우트·컴포넌트가 바뀌는지, 기존 포스트 MDX 렌더에 영향이 있는지 |
| 계획 | 방향과 버린 대안, 구조가 바뀌면 UML 다이어그램(클래스·시퀀스), 작업 순서(작업마다 파일·검증 명령·기대 결과), 검증(단위 테스트·e2e, 버그면 재현을 고정할 테스트), 완료 조건 체크리스트 |
| N차완료 | 계획의 목적이 해결됐는지, 무엇을 바꿨는지(파일별 표), 실행한 검증 명령과 결과, 버그면 재현 테스트의 실패·통과 출력, 남은 것 |
| N차리뷰및개선 | 지적한 것과 출처(자가 리뷰·PR 리뷰), 항목마다 반영했는지와 그 근거, 리뷰에서 방향이 뒤집혔으면 무엇을 왜 바꿨는지 |
| PR 본문 | 계획의 완료 조건 체크리스트를 대조한 결과 |

## 원인분석

버그를 실제로 재현한 뒤, 재현 결과를 첨부해 사용자가 바로 이해할 수 있게 한다. 브라우저에서
재현한 **화면 이미지를 첨부한다**(`images/`). 재현 환경(URL·뷰포트 크기·다크모드 여부·브라우저)도
적어, 나중에 같은 자리에서 다시 돌릴 수 있게 한다. 반응형 문제면 재현한 뷰포트 폭을 숫자로 적는다.

## 계획

- **방향** — 후보를 몇 개 놓고 무엇으로 갈지 고른다. **버린 대안과 그 이유를 함께 적는다.** 코드는
  지금 무엇을 하는지 알려주지만 무엇을 해봤다가 실패했는지는 못 알려준다. 실측한 수치가 있으면
  같이 적고 어디서 쟀는지도 남긴다.
- **UML 다이어그램** — 계획이 페이지·컴포넌트·모듈을 새로 만들거나 그 역할·관계·호출 흐름을
  바꾸면, 아래 둘을 Mermaid 코드 블록으로 넣는다. 구조가 바뀌지 않는 작업(조건 하나를 고치는 버그
  수정, 스타일만 고치는 작업)은 넣지 않고 그 이유를 한 줄 적는다.
  - 클래스 다이어그램 하나 — 관여하는 페이지·컴포넌트·모듈을 클래스로 그리고 주요 props·함수와 그
    사이의 관계를 적는다. 관계는 포함(`*--`, 컴포넌트가 다른 컴포넌트를 렌더함)과 호출 의존(`..>`,
    모듈의 함수를 불러 씀)으로 나눠 그리고, 기호의 뜻을 그림 아래에 한 줄로 적는다. 새로 만드는
    것에는 `<<신규>>`, 바뀌는 것에는 `<<변경>>`을 단다.
  - 시퀀스 다이어그램 — 페이지 요청 처리나 사용자 조작처럼 주요 흐름마다 하나. 누가 누구를 어떤
    순서로 부르고 무엇을 돌려받는지 그린다. 반환은 점선(`-->>`)으로 그린다.
  - 클래스 다이어그램에는 반환 경로를 화살표로 그리지 않는다. 그리면 값을 돌려주는 쪽이 받는 쪽을
    참조하는 것처럼 읽힌다.
  - 다이어그램은 호출한 세션이 그려서 담을 내용으로 넘긴다. 받은 다이어그램은 고치지 않고 그대로
    싣는다.
- **작업 순서** — 작업은 작게 나눈다. 한 작업은 검증 명령 하나로 끝났는지 판단할 수 있는 가장 작은
  단위다.
  작업마다 고칠 파일(줄 범위까지)과 테스트 파일, 실행할 검증 명령과 기대 결과를 적고, 코드는
  적지 않는다. 검증 명령을 실행해 기대 결과가 나오면 그 작업은 끝난 것이다.
- **검증** — 단위 테스트와 e2e 로 무엇을 어떻게 확인할지. 버그면 원인 분석에서 재현한 증상을
  어떤 테스트로 고정할지 적는다.
- **완료 조건 체크리스트** — 아래 표를 채운다.

| 항목 | 판단 기준 |
| --- | --- |
| 구현 | 항상 |
| 단위 테스트 (Jest) | 항상 |
| e2e (Playwright) | 화면으로 확인되는 변경이면 |
| 브라우저 확인 | 눈으로 확인할 게 있나 |
| 반응형 · 다크모드 | UI 변경이면 |
| 접근성 | 상호작용 요소나 포커스 흐름이 바뀌나 |
| 기존 포스트 MDX | 포스트 렌더 결과가 바뀌나 |
| 문서 갱신 | CLAUDE.md · README 의 규칙이나 구조가 바뀌나 |

각 항목에 "필요 / 불필요"와 근거 한 줄을 단다.

## N차완료

결론은 계획에 적은 목적이 해결됐는지로 시작한다. 계획의 표를 그대로 옮기지 않는다. 코드의 모양이
어떻게 바뀌었는지(줄 수·파일 수)가 아니라, 그 변경으로 무엇이 가능해졌는지를 첫 문장에 쓴다.

검증 결과는 `/start` 3단계의 네 명령(lint·타입 검사·단위 테스트·e2e) 결과를 적는다. 버그를
고쳤다면 재현 테스트의 실패 출력과 수정 후 통과 출력을 본문에 남긴다. 테스트로 고정할 수 없는 버그는
그 이유를 적는다.

## N차리뷰및개선

리뷰 회차마다 새 문서를 만든다. 리뷰 지적은 항목마다 반영할지 말지와 그 근거를 적는다. 리뷰에서
방향이 뒤집히면 무엇을 왜 바꿨는지 이 문서에 적는다. 계획 문서는 고치지 않는다.

## PR 본문

2단계 완료 조건 체크리스트에서 필요하다고 적은 항목마다, 이 PR 에 들어갔는지를 표시한다.

# 수정 금지

각 단계의 산출물은 그 단계가 끝난 뒤 고치지 않는다. 결정이 번복되면 이전 문서를 고치는 대신
다음 연번 문서에 새 내용을 적는다. 리뷰 내용이 뒤집히는 경우도 다음 회차 문서에 적는다. 범위가
늘어 다시 구현했으면 다음 회차 완료 문서(`NN-2차완료.md`)를 새로 만들고 1차 완료 문서는 고치지
않는다.

진행 중인 단계의 문서는 그 단계가 끝나기 전까지 고쳐도 된다. 끝난 뒤에도 고쳐 쓰는 예외는
`temp-memory.md` 하나다.

# 다듬기

- 산출물과 PR 본문은 작성 후 `/refine-korean` 스킬과 korean-concise output style 로 다듬는다.
- 다듬은 뒤 처음부터 끝까지 다시 읽는다. 이 문서의 규칙을 전부 지키는지, 어색한 내용이 없는지
  전면 검토하고 전부 만족할 때까지 고친다.
